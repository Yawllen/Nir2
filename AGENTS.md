# AGENTS.md — рабочий стандарт для `Nir2`

## 1) Назначение

Этот файл задает постоянные правила работы агента в репозитории:
- как выполнять задачи;
- как оформлять изменения;
- как проводить аудит;
- когда можно делать commit/push.

Если запрос пользователя конфликтует с этим файлом, приоритет у явного запроса пользователя, кроме случаев небезопасных или разрушительных действий.

## 2) Язык и стиль

- Рабочий язык: русский.
- Комментарии в коде и документации: русский, лаконично, только по делу.
- Сообщения коммитов: русский.
- Описание коммита (body): русский, с кратким пояснением что/зачем/как проверено.
- Коммуникация: коротко и технически точно, без воды.

## 2.1) Локальная среда агента

- Базовая локальная среда: Windows 11, shell: PowerShell.
- При локальном выполнении учитывать синтаксис PowerShell (`;`, экранирование, кавычки, пути).
- Для LaTeX-проверок использовать установленный MiKTeX backend.
- При правках `AGENTS.md` сохранять UTF-8 без потери кириллицы; перед ответом проверять, что текст читается корректно.

## 3) Ветки и Git-дисциплина

- Основная рабочая ветка: `main`, если пользователь не указал другую.
- `push` выполнять только после явного разрешения пользователя (`"коммить и пуш"`, `"пуш"` и т.п.).
- `commit` допустим в рамках задачи.
- Не делать `amend`, `rebase`, `reset --hard`, удаление веток и другие потенциально опасные git-операции без явного запроса.
- Не откатывать чужие изменения без прямого указания.

## 4) Формат выполнения задач

### 4.1 Если запрос = аудит

- Режим read-only: без правок файлов.
- Выводить findings с приоритетом `P0 -> P1 -> P2`.
- Для каждого finding фиксировать:
  - факт;
  - риск;
  - действие;
  - доказательство (путь/строка).

### 4.2 Если запрос = правки

- Менять только то, что нужно для задачи, без лишнего рефакторинга.
- Сначала выполнить правки, затем проверить логику/структуру/синтаксис.
- Перед коммитом показать краткий результат проверки.

## 5) Минимальные проверки перед commit

- Для изменений, затрагивающих LaTeX-пайплайн или содержимое работы, выполнять базовый цикл:
  1. `pdflatex Thesis.tex`
  2. `biber Thesis`
  3. `pdflatex Thesis.tex`
  4. `pdflatex Thesis.tex`
- Требование: отсутствие fatal errors и успешный exit code каждого шага.
- Если часть проверок невозможно выполнить локально, явно указать это в итоге.

## 6) Доменные правила проекта (LaTeX/НИР)

- Точка входа сборки: `Thesis.tex`.
- Библиография: `biblatex-gost + biber`, база источников: `Bib.bib`.
- Сохранять структуру и именование шаблона:
  - `Thesis.tex`, `Title.tex`, `Intro.tex`, `Chapter1.tex`, `Chapter2.tex`, `Chapter3.tex`, `Conclusion.tex`, `Progress.tex`, `Appendix.tex`, `VolSU.rtx`, `fig/`.
- Не менять стиль оформления, движок и схему сборки без явного запроса пользователя.
- Не удалять и не переразбивать главы/разделы научной работы без прямой задачи.
- При правках содержимого НИР сохранять фактическую корректность ссылок, цитирования и структуру документа.

## 7) Заготовка правил генерации текста НИР (анти-ИИ-стиль)

Цель раздела: временный каркас для будущих правил генерации/редактирования текста без явного ИИ-стиля.

### 7.1 Карта текущей структуры работы

- Введение: `Intro.tex`
- Глава 1: `Chapter1.tex`
- Глава 2: `Chapter2.tex`
- Глава 3: `Chapter3.tex`
- Заключение: `Conclusion.tex`
- Ход выполнения практики: `Progress.tex`
- Приложения: `Appendix.tex`
- Источники: `Bib.bib`
- Титульные данные: `Title.tex`

### 7.2 Временные placeholder-правила

- `TODO: правила стиля фраз`
- `TODO: запреты на шаблонные AI-обороты`
- `TODO: требования к фактам/ссылкам из Bib.bib`
- `TODO: правила редактирования существующего текста vs генерации нового`

## 8) Документация

- Обновлять документацию только если она затронута текущей задачей или явно запрошена.
- Не переписывать docs без необходимости.
- При правках docs сохранять соответствие фактическому коду и LaTeX-пайплайну.

## 9) Запрещено без явного запроса

- Пушить в удаленный репозиторий.
- Выполнять разрушительные операции с рабочим деревом или историей.
- Массово менять стиль/структуру научного текста вне рамок задачи.

## 10) Definition of Done

Задача считается завершенной, когда:
- выполнено ровно то, что запросил пользователь;
- изменения согласованы с текущим устройством `Nir2` и его LaTeX-шаблоном;
- проверки и ограничения явно отражены в отчете;
- commit/push выполнены только по политике этого файла.
