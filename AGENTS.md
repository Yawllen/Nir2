# AGENTS.md — рабочий стандарт для `Nir2`

## 1) Назначение

Этот файл задает постоянные правила работы агента в репозитории:
- как выполнять задачи;
- как оформлять изменения;
- как проводить аудит;
- когда можно делать commit/push.

Если запрос пользователя конфликтует с этим файлом, приоритет у явного запроса пользователя, кроме случаев небезопасных или разрушительных действий.

## 2) Язык и стиль

- Рабочий язык: русский.
- Комментарии в коде и документации: русский, лаконично, только по делу.
- Сообщения коммитов: русский.
- Описание коммита (body): русский, с кратким пояснением что/зачем/как проверено.
- Коммуникация: коротко и технически точно, без воды.

## 2.1) Локальная среда агента

- Базовая локальная среда: Windows 11, shell: PowerShell.
- При локальном выполнении учитывать синтаксис PowerShell (`;`, экранирование, кавычки, пути).
- Для LaTeX-проверок использовать установленный MiKTeX backend.
- При правках `AGENTS.md` сохранять UTF-8 без потери кириллицы; перед ответом проверять, что текст читается корректно.

## 3) Ветки и Git-дисциплина

- Основная рабочая ветка: `main`, если пользователь не указал другую.
- `push` выполнять только после явного разрешения пользователя (`"коммить и пуш"`, `"пуш"` и т.п.).
- `commit` допустим в рамках задачи.
- Не делать `amend`, `rebase`, `reset --hard`, удаление веток и другие потенциально опасные git-операции без явного запроса.
- Не откатывать чужие изменения без прямого указания.

## 4) Формат выполнения задач

### 4.1 Если запрос = аудит

- Режим read-only: без правок файлов.
- Выводить findings с приоритетом `P0 -> P1 -> P2`.
- Для каждого finding фиксировать:
  - факт;
  - риск;
  - действие;
  - доказательство (путь/строка).

### 4.2 Если запрос = правки

- Менять только то, что нужно для задачи, без лишнего рефакторинга.
- Сначала выполнить правки, затем проверить логику/структуру/синтаксис.
- Перед коммитом показать краткий результат проверки.

### 4.3 Если запрос = генерация текста НИР

- Сначала всегда выдавать текст в чат (черновик/чистовой вариант) без автоматической записи в файлы репозитория.
- Изменения в `Intro.tex`, `Chapter*.tex`, `Conclusion.tex`, `Progress.tex` вносить только после явного подтверждения пользователя.
- По умолчанию предполагается, что пользователь сам переносит текст в репозиторий, если не дал прямую команду сделать это агенту.
- Текст в чат отправлять абзацами без ручных переносов внутри абзаца, чтобы при вставке в `.tex` абзац не дробился на множество строк.

## 5) Минимальные проверки перед commit

- Для изменений, затрагивающих LaTeX-пайплайн или содержимое работы, выполнять базовый цикл:
  1. `pdflatex Thesis.tex`
  2. `biber Thesis`
  3. `pdflatex Thesis.tex`
  4. `pdflatex Thesis.tex`
- Требование: отсутствие fatal errors и успешный exit code каждого шага.
- Если часть проверок невозможно выполнить локально, явно указать это в итоге.
- Временные файлы проверок (`build_*.txt`, `build_*.log`, `tmp_*.txt` и аналогичные служебные логи) после фиксации результата удалять из рабочего дерева.
- Не включать временные файлы проверок в `commit`; если такие файлы появились, очищать их перед фиксацией изменений.

## 6) Доменные правила проекта (LaTeX/НИР)

- Точка входа сборки: `Thesis.tex`.
- Библиография: `biblatex-gost + biber`, база источников: `Bib.bib`.
- Сохранять структуру и именование шаблона:
  - `Thesis.tex`, `Title.tex`, `Intro.tex`, `Chapter1.tex`, `Chapter2.tex`, `Chapter3.tex`, `Chapter4.tex`, `Conclusion.tex`, `Progress.tex`, `Appendix.tex`, `VolSU.rtx`, `fig/`.
- Не менять стиль оформления, движок и схему сборки без явного запроса пользователя.
- Не удалять и не переразбивать главы/разделы научной работы без прямой задачи.
- При правках содержимого НИР сохранять фактическую корректность ссылок, цитирования и структуру документа.

### 6.1.1) Правила ссылок, таблиц и рисунков

- Для каждого рисунка и таблицы ссылка в основном тексте размещается непосредственно перед объектом и в финальной верстке находится на той же странице, что и объект.
- Если объект уходит на другую страницу, агент обязан локально скорректировать верстку (положение float, плотность/объем соседнего текста), чтобы восстановить совместное размещение ссылки и объекта.
- Не использовать `\begin{minipage}{...}` как способ принудительно удержать рисунок/таблицу рядом со ссылкой; совместное размещение обеспечивать стандартными окружениями `figure/table`, параметрами размещения float и точечными правками объема текста или масштаба объекта.
- Правило `строка не начинается с цифры или ссылки` применяется к основному тексту (`Intro.tex`, `Chapter*.tex`, `Conclusion.tex`, `Progress.tex`), но не к заголовкам, подписям, таблицам и листингам; исключение: устойчивые термины вида `3D-печать` и `3D-принтер` допускаются в начале строки.
- Для предотвращения висячих переносов использовать неразрывные пробелы: `рисунке~\ref{...}`, `таблице~\ref{...}`, `см.~\cite{...}`, `в~2026~году`, `20~\%`, `№~1`.
- Не начинать абзац с числа (кроме устойчивых терминов вида `3D-печать`), `\ref` или `\cite`; перед числом или ссылкой использовать вводную словесную конструкцию.
- Если в таблице используются буквенные обозначения (`U`, `P`, `I`, `t` и т.п.), сразу после таблицы добавлять курсивный блок `Примечание` с расшифровкой всех используемых обозначений и единиц измерения.
- Формат примечания фиксированный: `\noindent\textit{Примечание. ...}`; в тексте примечания ссылаться на таблицу в виде `в таблице~\ref{...}`.

### 6.3) Этапный план НИР и диплома (фиксированный контекст)

- НИР 1: **MVP + валидируемая детекция дефектов**.
  - Фокус: базовый рабочий контур принтера, подготовка данных, первичная модель детекции дефектов.
  - Результат: воспроизводимый MVP и подтверждаемая работоспособность детекции на тестовых сценариях.
- НИР 2: **интегрированный автономный контур печати**.
  - Фокус: интеграция обученной модели в цикл печати, очередь заданий, автоснятие детали, переход к следующему заданию.
  - Результат: связанный контур "печать -> контроль -> решение -> продолжение цикла" с минимальным участием оператора.
- Диплом: **завершенная система + измеримый эффект**.
  - Фокус: объединение всех подсистем в единый комплекс, проверка устойчивости и эксплуатационной пригодности.
  - Результат: целостный прототип и количественно подтвержденный эффект (качество, время, доля автоматизации).

- При генерации текста глав и введения явно привязывать формулировки к соответствующему этапу (`НИР 1`, `НИР 2`, `Диплом`), чтобы не смешивать цели и результаты разных этапов.

## 7) Заготовка правил генерации текста НИР (анти-ИИ-стиль)

Цель раздела: временный каркас для будущих правил генерации/редактирования текста без явного ИИ-стиля.

### 7.1 Карта текущей структуры работы

- Введение: `Intro.tex`
- Глава 1: `Chapter1.tex`
- Глава 2: `Chapter2.tex`
- Глава 3: `Chapter3.tex`
- Глава 4: `Chapter4.tex`
- Заключение: `Conclusion.tex`
- Ход выполнения практики: `Progress.tex`
- Приложения: `Appendix.tex`
- Источники: `Bib.bib`
- Титульные данные: `Title.tex`

### 7.2 Краткие анти-ИИ-правила (рабочая версия)

- Писать нейтрально и конкретно: без пафоса, символизма и рекламных эпитетов без точного подтверждения источником.
- Не использовать безатрибутивные формулы (`эксперты считают`, `некоторые критики`) и обобщения про известность/освещение без конкретных публикаций.
- Удалять редакционную болтовню (`в этом разделе рассмотрим...`), самореферат текста и шаблонные фразы про `перспективы в будущем`.
- Избегать речевых штампов: `не только..., но и...`, `это не просто..., это...`, искусственного `правила трех`, пафосных диапазонов `от и до`.
- Каждый абзац должен содержать проверяемый факт; неподтверждаемые утверждения удалять или переформулировать.
- Не выдумывать источники, DOI, ISBN, URL; не добавлять UTM-метки в ссылки.
- Не использовать результаты AI-детекторов как доказательство качества или истинности текста.

Источник принципов: `https://ru.wikipedia.org/wiki/Википедия:Признаки_сгенерированности_текста`.

### 7.3 Лексические правила НИР (русский язык)

- Использовать единые базовые термины:
  - `3D-печать`, `3D-принтер`, `аддитивное производство`, `дефект печати`, `контур печати`, `очередь печати`.
- Не использовать форму `трехмерной (3D) печати`; корректно: `3D-печать` или `трехмерная печать` (без дублирования в скобках).
- При первом упоминании аббревиатуры давать расшифровку в формате:
  - `метод послойного наплавления (Fused Deposition Modeling, FDM)`;
  - `минимально жизнеспособный продукт (Minimum Viable Product, MVP)`;
  - `искусственный интеллект (ИИ)`.
- После первого упоминания использовать только принятую аббревиатуру/термин, не менять обозначение по тексту.
- Для дефектов использовать нейтральные инженерные формулировки на русском языке; в тексте НИР не использовать англоязычные названия дефектов. Целевые дефекты фиксируются как: `отлипание модели от стола`, `растрескивание`, `дефект типа «спагетти»`, `смещение слоев`.
- В основном тексте НИР использовать только типографские кавычки-ёлочки (`«...»`); не использовать двойные кавычки (`"..."`).
- Исключить разговорную лексику и жаргон:
  - не писать `косяк`, `железо`, `видос`, `пофиксить`, `штука`;
  - писать `дефект`, `аппаратная часть`, `видеопоток`, `устранить`.
- Формулировки держать в научном регистре:
  - использовать `в рамках работы`, `показано`, `получено`, `установлено`;
  - избегать `я сделал`, `мы прикрутили`, `очень круто`, `сильно лучше`.
- Не применять оценочные усилители без метрик:
  - `значительно`, `существенно`, `кратно`, `эффективно` использовать только при наличии измеримого критерия или ссылки на источник.
- Числовые данные давать конкретно:
  - `до 25\%` вместо `очень высокий процент`;
  - диапазоны и сравнения указывать только при наличии основания (эксперимент, лог, источник).

### 7.4 Правила построения предложений (русский научный стиль)

- Принцип `одно предложение = одна завершенная мысль`; не объединять в одну фразу несколько разных тезисов.
- Рабочая длина предложения: `12-25` слов; предложения длиннее `30` слов разбивать на `2` фразы.
- Порядок изложения внутри абзаца: `факт -> пояснение -> следствие`; избегать скачков между темами.
- Не использовать более двух придаточных подряд и длинные цепочки с множественными `который/что`.
- Предпочитать нейтральные конструкции:
  - `показано`, `установлено`, `получено`, `выполнено`;
  - избегать разговорных личных форм `я сделал`, `мы придумали`.
- Согласовывать времена:
  - описание предметной области и общих положений -- настоящее время;
  - выполненные действия в рамках НИР -- прошедшее время.
- Связки использовать дозированно и по смыслу:
  - допустимо: `следовательно`, `таким образом`, `в результате`, `при этом`;
  - не повторять одну и ту же связку в соседних предложениях.
- При перечислении трех и более однотипных элементов использовать список (`itemize`), а не длинную фразу через запятые.
- Избегать двойных отрицаний, риторических вопросов и эмоционально-оценочных конструкций.
- Не допускать строк в основном тексте, начинающихся с цифры или ссылки; исключение: устойчивые термины вида `3D-печать` и `3D-принтер`; использовать неразрывные пробелы для связки предлога или слова с числом и ссылкой.
- Каждый абзац завершать локальным выводом, связанным с задачей текущего раздела.
