# AGENTS.md — рабочий стандарт для `Nir2`

## 1) Назначение

Этот файл задает постоянные правила работы агента в репозитории:
- как выполнять задачи;
- как оформлять изменения;
- как проводить аудит;
- когда можно делать commit/push.

Если запрос пользователя конфликтует с этим файлом, приоритет у явного запроса пользователя, кроме случаев небезопасных или разрушительных действий.

## 2) Язык и стиль

- Рабочий язык: русский.
- Комментарии в коде и документации: русский, лаконично, только по делу.
- Сообщения коммитов: русский.
- Описание коммита (body): русский, с кратким пояснением что/зачем/как проверено.
- Коммуникация: коротко и технически точно, без воды.

## 2.1) Локальная среда агента

- Базовая локальная среда: Windows 11, shell: PowerShell.
- При локальном выполнении учитывать синтаксис PowerShell (`;`, экранирование, кавычки, пути).
- Для LaTeX-проверок использовать установленный MiKTeX backend.
- При правках `AGENTS.md` сохранять UTF-8 без потери кириллицы; перед ответом проверять, что текст читается корректно.

## 3) Ветки и Git-дисциплина

- Основная рабочая ветка: `main`, если пользователь не указал другую.
- `push` выполнять только после явного разрешения пользователя (`"коммить и пуш"`, `"пуш"` и т.п.).
- `commit` допустим в рамках задачи.
- Не делать `amend`, `rebase`, `reset --hard`, удаление веток и другие потенциально опасные git-операции без явного запроса.
- Не откатывать чужие изменения без прямого указания.

## 4) Формат выполнения задач

### 4.1 Если запрос = аудит

- Режим read-only: без правок файлов.
- Выводить findings с приоритетом `P0 -> P1 -> P2`.
- Для каждого finding фиксировать:
  - факт;
  - риск;
  - действие;
  - доказательство (путь/строка).

### 4.2 Если запрос = правки

- Менять только то, что нужно для задачи, без лишнего рефакторинга.
- Сначала выполнить правки, затем проверить логику/структуру/синтаксис.
- Перед коммитом показать краткий результат проверки.

### 4.3 Если запрос = генерация текста НИР

- Если пользователь просит подготовить новый текст без прямой команды записать его в файлы, сначала выдавать вариант в чат.
- Изменения в `Intro.tex`, `Chapter*.tex`, `Conclusion.tex`, `Progress.tex` вносить только после явного подтверждения пользователя.
- Прямые команды «исправь», «примени», «замени» или «внеси в текст» в контексте обсуждаемых правок считать разрешением на их внесение. Не запрашивать повторное подтверждение уже согласованного действия.
- По умолчанию предполагается, что пользователь сам переносит текст в репозиторий, если не дал прямую команду сделать это агенту.
- Текст в чат отправлять абзацами без ручных переносов внутри абзаца, чтобы при вставке в `.tex` абзац не дробился на множество строк.

## 5) Минимальные проверки перед commit

- Для изменений, затрагивающих LaTeX-пайплайн или содержимое работы, выполнять базовый цикл:
  1. `pdflatex Thesis.tex`
  2. `biber Thesis`
  3. `pdflatex Thesis.tex`
  4. `pdflatex Thesis.tex`
- Требование: отсутствие fatal errors и успешный exit code каждого шага.
- Если часть проверок невозможно выполнить локально, явно указать это в итоге.
- Временные файлы проверок (`build_*.txt`, `build_*.log`, `tmp_*.txt` и аналогичные служебные логи) после фиксации результата удалять из рабочего дерева.
- Не включать временные файлы проверок в `commit`; если такие файлы появились, очищать их перед фиксацией изменений.

## 6) Доменные правила проекта (LaTeX/НИР)

- `VolSU.rtx` задает общий шаблон и единые правила оформления всей научной работы. При оформлении глав и служебных частей документа учитывать настройки этого шаблона.
- Библиография: `biblatex-gost + biber`, база источников: `Bib.bib`.
- Сохранять структуру и именование шаблона:
  - `Thesis.tex`, `Title.tex`, `Intro.tex`, `Chapter1.tex`, `Chapter2.tex`, `Chapter3.tex`, `Chapter4.tex`, `Conclusion.tex`, `Progress.tex`, `Appendix.tex`, `VolSU.rtx`, `fig/`.
- Не менять стиль оформления, движок и схему сборки без явного запроса пользователя.
- Не удалять и не переразбивать главы/разделы научной работы без прямой задачи.
- При правках содержимого НИР сохранять фактическую корректность ссылок, цитирования и структуру документа.

### 6.1.1) Правила ссылок, таблиц и рисунков

- Для каждого рисунка и таблицы ссылка в основном тексте размещается непосредственно перед объектом и в финальной верстке находится на той же странице, что и объект.
- Если объект уходит на другую страницу, агент обязан локально скорректировать верстку (положение float, плотность/объем соседнего текста), чтобы восстановить совместное размещение ссылки и объекта.
- Не использовать `\begin{minipage}{...}` как способ принудительно удержать рисунок/таблицу рядом со ссылкой; совместное размещение обеспечивать стандартными окружениями `figure/table`, параметрами размещения float и точечными правками объема текста или масштаба объекта.
- Правило `строка не начинается с цифры или ссылки` применяется к основному тексту (`Intro.tex`, `Chapter*.tex`, `Conclusion.tex`, `Progress.tex`), но не к заголовкам, подписям, таблицам и листингам; исключение: устойчивые термины вида `3D-печать` и `3D-принтер` допускаются в начале строки.
- Для предотвращения висячих переносов использовать неразрывные пробелы: `рисунке~\ref{...}`, `таблице~\ref{...}`, `см.~\cite{...}`, `в~2026~году`, `20~\%`, `№~1`.
- Не начинать абзац с числа (кроме устойчивых терминов вида `3D-печать`), `\ref` или `\cite`; перед числом или ссылкой использовать вводную словесную конструкцию.
- Если в таблице используются буквенные обозначения (`U`, `P`, `I`, `t` и т.п.), сразу после таблицы добавлять курсивный блок `Примечание` с расшифровкой всех используемых обозначений и единиц измерения.
- Формат примечания фиксированный: `\noindent\textit{Примечание. ...}`; в тексте примечания ссылаться на таблицу в виде `в таблице~\ref{...}`.

### 6.3) Этапный план НИР и диплома (фиксированный контекст)

- НИР 1: **MVP + валидируемая детекция дефектов**.
  - Фокус: базовый рабочий контур принтера, подготовка данных, первичная модель детекции дефектов.
  - Результат: воспроизводимый MVP и подтверждаемая работоспособность детекции на тестовых сценариях.
- НИР 2: **интегрированный автономный контур печати**.
  - Фокус: интеграция обученной модели в цикл печати, очередь заданий, автоснятие детали, переход к следующему заданию.
  - Результат: связанный контур "печать -> контроль -> решение -> продолжение цикла" с минимальным участием оператора.
- Диплом: **завершенная система + измеримый эффект**.
  - Фокус: объединение всех подсистем в единый комплекс, проверка устойчивости и эксплуатационной пригодности.
  - Результат: целостный прототип и количественно подтвержденный эффект (качество, время, доля автоматизации).

- Разграничивать цели и результаты этапов по содержанию. В основном научном тексте не использовать обозначения `НИР 1`, `НИР 2` и `Диплом` как поясняющие ярлыки.

### 6.4) Фиксированный состав глав и подглав (утверждено)

- Распределение содержания по главам:
  - Глава 1: обзор предметной области, технологии печати, дефектов и существующих подходов к контролю.
  - Глава 2: сравнение существующих решений и теоретическое обоснование собственного подхода. Здесь описываются требования, архитектура, выбор компонентов, инструментов и моделей, принципы подготовки данных, план обучения и критерии проверки.
  - Главы 3 и 4: реализация выбранного решения, фактически выполненные действия, испытания, полученные результаты и ограничения.
- При проверке главы 2 не считать описание выбранных методов, подготовки данных или планируемого обучения преждевременным только из-за наличия глав реализации. Не требовать экспериментального подтверждения непосредственно в главе 2; результаты испытаний приводятся в главах 3 и 4. Теоретический выбор должен быть объяснен, а планируемые свойства не должны выдаваться за измеренные результаты.

- Утвержденные названия глав (финальный вариант):

## 7) Правила написания и редактирования научного текста

Эти правила применяются к научному тексту работы. README и техническая документация следуют общим правилам русского текста и могут содержать необходимые команды, имена файлов и API.

### 7.1 Карта текущей структуры работы

- Введение: `Intro.tex`
- Глава 1: `Chapter1.tex`
- Глава 2: `Chapter2.tex`
- Глава 3: `Chapter3.tex`
- Глава 4: `Chapter4.tex`
- Заключение: `Conclusion.tex`
- Ход выполнения практики: `Progress.tex`
- Приложения: `Appendix.tex`
- Источники: `Bib.bib`
- Титульные данные: `Title.tex`

### 7.2 Естественный русский язык и фактическая точность

- Писать нейтрально и конкретно: без пафоса, символизма и рекламных эпитетов без точного подтверждения источником.
- Не использовать безатрибутивные формулы (`эксперты считают`, `некоторые критики`) и обобщения про известность/освещение без конкретных публикаций.
- Удалять редакционную болтовню (`в этом разделе рассмотрим...`), самореферат текста и шаблонные фразы про `перспективы в будущем`.
- Избегать речевых штампов: `не только..., но и...`, `это не просто..., это...`, искусственного `правила трех`, пафосных диапазонов `от и до`.
- Не добавлять вводные и заключительные абзацы ради объема. Сохранять полезные объяснения, условия эксперимента, результаты и ограничения; не заменять их общими рассуждениями.
- Проверять канцелярские и шаблонные обороты по смыслу, а не по списку запрещенных слов. Сохранять точные научные термины, даже если в другом контексте они звучат формально.
- Каждый абзац должен содержать проверяемый факт; неподтверждаемые утверждения удалять или переформулировать.
- Не выдумывать источники, DOI, ISBN, URL; не добавлять UTM-метки в ссылки.
- Для научных ссылок использовать авторитетные научные статьи, книги и материалы научных конференций. Сайты производителей и документация программ могут служить для проверки технических сведений, но не заменяют научные источники в библиографии работы.
- В связном тексте при указании авторов приводить полные имена в соответствии с источником либо называть публикацию. Избегать формулировок вида «в исследовании Кима и соавторов» без полных имен. При повторном обращении допустимо «в работе~\cite{...}».
- Не использовать результаты AI-детекторов как доказательство качества или истинности текста.

Источник принципов: `https://ru.wikipedia.org/wiki/Википедия:Признаки_сгенерированности_текста`.

### 7.3 Лексические правила НИР (русский язык)

- В основном научном тексте не указывать названия репозиториев, файлов, локальные пути и внутренние идентификаторы версий экспериментов. Описывать назначение и полученный результат; названия моделей и научных методов допустимы.
- Внешний набор кадров, добавленных к собственным изображениям, описывать без его собственного названия: «открытый размеченный набор изображений». Сохранять сведения о количестве, разметке и происхождении; название базы предварительного обучения ImageNet допускается.
- В главе 1 давать обзор, в главе 2 — сравнение решений и теоретическое обоснование собственного подхода, в главах 3 и 4 — реализацию и испытания. Различать планируемые действия и фактически полученные результаты. Не заменять фактическое описание общими рассуждениями. При переработке сохранять объем каждого затронутого раздела не меньше исходного, если пользователь явно не просит сокращение.

- Использовать единые базовые термины:
  - `3D-печать`, `3D-принтер`, `аддитивное производство`, `дефект печати`, `контур печати`, `очередь печати`.
- Не использовать форму `трехмерной (3D) печати`; корректно: `3D-печать` или `трехмерная печать` (без дублирования в скобках).
- При первом упоминании программы, библиотеки, модели, метода, компании, набора данных или другого специального названия пояснять на русском языке, что это и какую роль оно выполняет в работе. Иностранные термины давать с русским переводом и, при необходимости, оригинальным названием в скобках. Торговые названия программ, продуктов и компаний сохранять в оригинале и сопровождать русским пояснением назначения; не придумывать буквальные переводы названий.
- При первом упоминании каждого терминологического сокращения в порядке чтения работы давать полное русское название, а для английского сокращения также исходную расшифровку. Проверять основной текст, таблицы и подписи: пояснение должно предшествовать первому использованию сокращения в объекте. Обозначения моделей, торговые названия, единицы измерения и команды не снабжать выдуманными расшифровками. Формат:
  - `метод послойного наплавления (Fused Deposition Modeling, FDM)`;
  - `минимально жизнеспособный продукт (Minimum Viable Product, MVP)`;
  - `искусственный интеллект (ИИ)`.
- После первого упоминания использовать только принятую аббревиатуру/термин, не менять обозначение по тексту.
- Для дефектов использовать нейтральные инженерные формулировки на русском языке; в тексте НИР не использовать англоязычные названия дефектов. Целевые дефекты фиксируются как: `отлипание модели от стола`, `растрескивание`, `дефект типа «спагетти»`, `смещение слоев`.
- В основном тексте НИР использовать только типографские кавычки-ёлочки (`«...»`); не использовать двойные кавычки (`"..."`).
- Во всех LaTeX-исходниках работы и шаблона пунктуационное тире оформлять командой `\textemdash{}`, а не символами `—`/`–` или последовательностями `---`/`--`. В связном тексте использовать неразрывный пробел перед тире: `слово~\textemdash{} пояснение`. Дефисы в терминах, именах и командах сохранять; для числовых диапазонов сохранять LaTeX-запись `--`.
- Исключить разговорную лексику и жаргон:
  - не писать `косяк`, `железо`, `видос`, `пофиксить`, `штука`;
  - писать `дефект`, `аппаратная часть`, `видеопоток`, `устранить`.
- Формулировки держать в научном регистре:
  - использовать конкретное описание действий и результатов; `показано`, `получено`, `установлено` оставлять там, где это точно передает смысл;
  - избегать `я сделал`, `мы прикрутили`, `очень круто`, `сильно лучше`.
- Не применять оценочные усилители без метрик:
  - `значительно`, `существенно`, `кратно`, `эффективно` использовать только при наличии измеримого критерия или ссылки на источник.
- Числовые данные давать конкретно:
  - `до 25\%` вместо `очень высокий процент`;
  - диапазоны и сравнения указывать только при наличии основания (эксперимент, лог, источник).

### 7.4 Правила построения предложений (русский научный стиль)

- Принцип `одно предложение = одна завершенная мысль`; не объединять в одну фразу несколько разных тезисов.
- Предпочитать короткие и средние предложения с естественным чередованием длины. Длинную фразу разбивать, если в ней несколько мыслей или трудно проследить связи; не подгонять каждое предложение под одинаковое число слов.
- Излагать факты и пояснения в логическом порядке, без скачков между темами. Не навязывать всем абзацам одинаковую схему и обязательное заключительное предложение.
- Не использовать более двух придаточных подряд и длинные цепочки с множественными `который/что`.
- Предпочитать нейтральные конструкции:
  - `показано`, `установлено`, `получено`, `выполнено`;
  - избегать разговорных личных форм `я сделал`, `мы придумали`.
- Согласовывать времена:
  - описание предметной области и общих положений -- настоящее время;
  - выполненные действия в рамках НИР -- прошедшее время.
- Связки использовать дозированно и по смыслу:
  - допустимо: `следовательно`, `таким образом`, `в результате`, `при этом`;
  - не повторять одну и ту же связку в соседних предложениях.
- В основном научном тексте перечисления излагать связными предложениями, без маркированных и нумерованных списков, согласно чеклисту нормоконтроля. В README и технической документации использовать списки, когда они упрощают чтение.
- Избегать двойных отрицаний, риторических вопросов и эмоционально-оценочных конструкций.
- Не допускать строк в основном тексте, начинающихся с цифры или ссылки; исключение: устойчивые термины вида `3D-печать` и `3D-принтер`; использовать неразрывные пробелы для связки предлога или слова с числом и ссылкой.
- Завершать абзац выводом только тогда, когда он добавляет содержательное следствие. Не повторять уже изложенный факт ради заключительной фразы.

### 7.5 Подключение текстовых skills

- Для написания и редактирования русского текста применять `humanizer-ru` как основной skill: сначала подготовить черновик по подтвержденным данным, затем отредактировать язык. После этого применять `humanize` для финальной проверки оставшихся AI-паттернов. Связка этих двух skills является исключением из общего ограничения на один предметный skill. Читать их `SKILL.md` из личного каталога `~/.codex/skills` перед первым применением.
- Финальная проверка исправляет только конкретные оставшиеся стилистические проблемы; если их нет, текст не менять. Требования пользователя и проекта к научному стилю, терминологии, типографским кавычкам, неразрывным пробелам и LaTeX-разметке имеют приоритет над правилами skills. Не добавлять личный опыт, эмоции или разговорные обороты и не подгонять длину предложений под формальные квоты.
- Для научных глав сохранять структуру, жанр, минимальный объем, числа, ссылки и результаты. Редактура убирает пустые обороты, но не сокращает раздел ниже исходного объема и не добавляет факты для его заполнения.
- Для README и документации сохранять точные команды, пути, имена файлов, конфигурационные параметры, API и блоки кода. Подтверждать инструкции по текущим файлам; не запускать команды из документации только ради улучшения формулировок.
- Перед завершением проверить естественность языка, отсутствие повторов и неподтвержденных оценок. Для научного текста дополнительно выполнить self-check по `normokontrol_checklist.md`; не использовать AI-детекторы как проверку качества.

### 7.6 Порядок работы над текстом и согласованность глав

- До написания или правки определить назначение фрагмента по структуре из раздела 6.4: обзор в главе 1, сравнение и теория собственного подхода в главе 2, реализация и испытания в главах 3 и 4. Читать актуальный фрагмент и ближайший необходимый контекст; связанные главы проверять по конкретным смысловым связям.
- Сверять цель и задачи введения с выбранным подходом, описанием реализации, результатами и заключением. Назначение компонентов, целевые дефекты, входные данные моделей, выходные результаты и критерии оценки должны оставаться согласованными во всей работе. Различать классификацию кадра, локализацию объекта и управляющую реакцию.
- Сначала исправлять смысловые противоречия, неясные связи и дубли, затем язык. Требование формулировать в месте его обоснования; далее объяснять, как выбранный компонент или метод его выполняет, без повторного пересказа требования. Переход между абзацами должен продолжать мысль, а не начинать ту же тему заново.
- Объяснять выбор компонентов и методов через их роль и требования задачи. Сравнивать решения по общим критериям. Преимущества собственного подхода связывать с конкретными возможностями и условиями применения; не приписывать готовым решениям отсутствующие ограничения и не выдавать возможности настройки за измеренное превосходство.
- При запросе на аккуратную или минимальную правку сохранять удачные формулировки, структуру и полезные подробности. Менять только фрагменты, в которых есть конкретная проблема. После удаления повторов сохранять содержательный объем раздела за счет необходимых пояснений, а не общих рассуждений или новых неподтвержденных фактов.
- После применения текстовых skills перечитать измененные абзацы вместе с соседними. Проверить связность, единообразие терминов, первое упоминание названий, различие плана и результата, числа, цитирование и LaTeX-разметку. В итоговом ответе кратко указать изменения, выполненные проверки и их пределы; сборку не представлять выполненной без фактического запуска.

## 8) Документация

- Обновлять документацию только если она затронута текущей задачей или явно запрошена.
- Не переписывать docs без необходимости.
- При правках docs сохранять соответствие фактическому коду и LaTeX-пайплайну.

## 9) Запрещено без явного запроса

- Пушить в удаленный репозиторий.
- Выполнять разрушительные операции с рабочим деревом или историей.
- Массово менять стиль/структуру научного текста вне рамок задачи.

## 10) Definition of Done

Задача считается завершенной, когда:
- выполнено ровно то, что запросил пользователь;
- изменения согласованы с текущим устройством `Nir2` и его LaTeX-шаблоном;
- проверки и ограничения явно отражены в отчете;
- commit/push выполнены только по политике этого файла.
